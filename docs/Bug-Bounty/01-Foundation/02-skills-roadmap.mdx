# Skills Roadmap: What to Learn, in What Order

`Bug Bounty` · `Stage 1 — Foundations` · `Level: L0 → L2` · `Reading time: ~12 min`

The biggest beginner mistake is learning tools before learning **how the web works**. Tools only show you requests; you need to understand those requests to see what's wrong with them.

## Layer 1 — HTTP and the Browser (Non-Negotiable)

You should be able to read any raw HTTP request and explain every line.

| Topic | What you must understand |
|---|---|
| Request/response structure | Method, path, query string, headers, body, status codes |
| Methods | `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS` — and that servers may treat them inconsistently |
| Headers that matter | `Host`, `Cookie`, `Set-Cookie`, `Authorization`, `Origin`, `Referer`, `Content-Type`, `X-Forwarded-For`, caching headers |
| Cookies | Attributes `HttpOnly`, `Secure`, `SameSite`, `Domain`, `Path` |
| Same-Origin Policy & CORS | Why one site can't read another's responses, and how CORS relaxes that |
| Encodings | URL encoding, HTML entities, Base64, Unicode — and double encoding |
| Content types | Form-encoded, multipart, JSON, XML |
| HTTPS basics | What TLS protects and what it doesn't |
| DevTools | Network tab, Storage, Console, Sources (with breakpoints) |

```http
POST /api/v1/users/42/email HTTP/1.1
Host: app.example.com
Cookie: session=7f3a…
Content-Type: application/json
Origin: https://app.example.com

{"email":"new@example.com"}
```

If you can look at that and immediately ask *"does the server check that user 42 is me?"* and *"is there CSRF protection on this?"*, you're thinking like a hunter.

## Layer 2 — How Web Applications Are Built

| Topic | Why it matters |
|---|---|
| Front-end frameworks (React, Angular, Vue, Next.js) | Where client-side routes, API calls and secrets hide in JavaScript bundles |
| Back-end frameworks (Express, Django, Rails, Spring, Laravel, ASP.NET) | Each has typical mistakes and typical error messages |
| REST and GraphQL APIs | Most modern bugs live in APIs, not HTML pages |
| Databases (SQL and NoSQL) | Needed to understand injection and data exposure |
| Authentication | Sessions vs tokens, JWTs, OAuth 2.0 / OpenID Connect, SAML, MFA |
| Authorization models | Roles, ownership, multi-tenancy — the source of IDOR and privilege bugs |
| Caches, CDNs, reverse proxies, WAFs | Source of cache, smuggling and bypass bugs |
| Cloud basics (AWS/GCP/Azure) | Storage buckets, metadata services, IAM |

<Admonition type="tip" title="Beginner lane">

The fastest way to understand web apps deeply is to **build a small one**: a login, a profile page, an "edit my note" API. Then try to break your own app. You'll understand IDOR and CSRF far better after writing the code that has them.

</Admonition>

## Layer 3 — Linux and the Command Line

Most recon tooling is command-line and runs best on Linux (or WSL on Windows, or a cheap cloud VPS).

Must-know: navigation, files and permissions, pipes and redirection, `grep`, `sort`, `uniq`, `sed`, `awk`, `cut`, `jq`, `curl`, `xargs`, background jobs, `tmux` or `screen`, environment variables, package managers, installing Go and Python tools.

```bash
# The kind of one-liner you'll write daily:
cat urls.txt | grep -E '\.js(\?|$)' | sort -u | tee js-files.txt | wc -l
```

The **[All about Linux](/docs/category/fundamentals)** pages in Fundamentals cover the shell basics.

## Layer 4 — Scripting

You don't need to be a software engineer, but you must be able to:

- glue tools together and process their output,
- write small proof-of-concept scripts (race conditions, CSRF pages, automated checks),
- read source code — JavaScript especially.

| Language | Use it for |
|---|---|
| **Bash** | Gluing recon tools together |
| **Python** | PoCs, custom scanners, parsing data (`requests`, `httpx`, `asyncio`) |
| **JavaScript** | Reading front-end code, XSS payloads, CSRF/postMessage PoCs |
| **Go** (optional) | Fast custom tooling; most modern recon tools are written in Go |

## Layer 5 — The Bug Classes

Learn bug classes **one at a time, deeply**, rather than all of them shallowly. A good order for beginners:

| Order | Bug class | Why this order |
|---|---|---|
| 1 | **IDOR / access control** | Most common paid bug class; needs no payloads — just logic |
| 2 | **Information disclosure & misconfiguration** | Easy to spot once you know where to look |
| 3 | **XSS** (reflected, stored, DOM) | Teaches contexts, encoding and the browser |
| 4 | **CSRF, CORS, open redirect** | Teaches browser security models |
| 5 | **Authentication flaws & account takeover** | Password reset, OAuth, 2FA — high impact |
| 6 | **Business logic & race conditions** | Rarely duplicated; needs app understanding |
| 7 | **SSRF** | High impact, common in modern cloud apps |
| 8 | **Injection** (SQLi, NoSQLi, SSTI, command) | Rarer now, but critical when found |
| 9 | **Advanced** — cache poisoning, request smuggling, deserialization, prototype pollution | Specialist territory, high payouts |

## The 90-Day Starter Plan

<Tabs>
<TabItem value="m1" label="Days 1–30" default>

**Goal: understand the web and your tools.**

- HTTP, cookies, sessions, same-origin policy, CORS.
- Install Burp Suite Community or Caido; proxy everything you do for a week and read the traffic.
- Linux basics and installing Go/Python tools.
- PortSwigger Web Security Academy: all **apprentice** labs for access control, authentication, information disclosure and XSS.
- Read 2–3 disclosed reports per day for the bug class you're studying.

</TabItem>
<TabItem value="m2" label="Days 31–60">

**Goal: go deep on two bug classes and start looking at real targets.**

- Practitioner-level labs for access control and XSS.
- Learn recon basics (Stage 2) and run them against **one** program's in-scope assets.
- Choose one VDP or a wide-scope public program. Spend at least two weeks on it.
- Map the app's features in a notes file. Test every feature for IDOR with two accounts.
- Expect duplicates and N/As. Read why, and adjust.

</TabItem>
<TabItem value="m3" label="Days 61–90">

**Goal: first valid report, and a repeatable routine.**

- Add authentication/ATO and business logic to your toolkit.
- Practise writing reports even for lab findings, using the template in Stage 5.
- Build a simple personal recon script.
- Set a weekly routine: e.g. 3 hunting sessions, 2 learning sessions, 1 write-up reading session.
- Submit carefully verified reports only. Quality builds the signal that brings private invites.

</TabItem>
</Tabs>

<Admonition type="info" title="Pro lane">

At higher levels, the skill that separates hunters is **specialisation**. Professionals often become known for one area — OAuth, cache poisoning, mobile, GraphQL, a specific technology like Salesforce or SAP — and go deeper there than anyone else. Depth in a niche beats general competence once you're past the basics.

</Admonition>

## Key Takeaways

- Learn HTTP and how web apps are built before you learn tools.
- Learn Linux and enough scripting to automate and write PoCs.
- Study bug classes one at a time, starting with access control.
- Combine labs, real disclosed reports and real targets every week.
